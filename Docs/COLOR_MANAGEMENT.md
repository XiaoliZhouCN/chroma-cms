# 色彩管理：设计与理由

> 本文回答**为什么这样设计**。精确的数学公式与常量在 [COLOR_SPEC.md](COLOR_SPEC.md)（规范性文件）。

## 1. 目标

把"像素值 → 屏幕上的光"这条链路的每一步都摊开、自己实现、可验证。

三条硬性约束（来自 [ADR-0004](adr/0004-self-implemented-color-management.md)）：

1. 转换全部发生在自写着色器里（HLSL 与 SkSL 各一套）。
2. 不使用 Skia 的 `SkColorSpace` 自动转换、不使用 Qt 的 `QColorSpace`、不依赖 Windows ICM 的自动映射。
3. 框架只允许做**声明**（这个表面是什么色彩空间），不允许做**转换**。

## 2. 概念清单（先分清，再写代码）

| 概念 | 含义 | 本项目里的落点 |
|---|---|---|
| **传输函数 (transfer)** | 编码值与光强的关系，不是"gamma" | Pass 1 解码、Pass 2 编码 |
| **色域 (primaries)** | RGB 三原色在 CIE xy 上的位置 + 白点 | 3×3 矩阵，经 XYZ 中转 |
| **矩阵 (YUV matrix)** | YCbCr 与 R'G'B' 的关系，601/709/2020 各不相同 | Pass 1 的 YUV→RGB |
| **范围 (range)** | limited(16-235) 还是 full(0-255) | Pass 1 归一化，**必须先做** |
| **位深 / 量化** | 8bpc、10bpc、16F | 中间目标 16F，末端按 ADR-0007 |
| **白点适应** | D65 ↔ D50 的色适应 | Bradford，仅在有 ICC 时启用 |
| **色调映射** | 高动态范围压到显示范围 | 二期 HDR；一期仅裁剪 + 说明 |
| **显示配置 (ICC)** | 屏幕实际能力 | 一期假定 sRGB；二期读 WCS |

## 3. 管线（两遍）

```
Pass 1（解到线性光）
  [采样] → [范围归一化] → [YUV→RGB] → [EOTF 解码]
         → [源色域→工作空间 矩阵] → [色调/色域映射]
         → RT: R16G16B16A16_FLOAT（线性，工作空间）

Pass 2（编到显示）
  [工作空间→显示色域 矩阵] → [显示 OETF 编码] → [抖动]
         → 交换链后台缓冲
```

**为什么分两遍**：把"线性光"做成显式中间产物，就能用 PIX 抓中间 RT 逐级比对，也把色彩管理与量化/抖动解耦。这是本项目最重要的可调试性设计。

## 4. 关键选择

### 4.1 工作空间 = 线性 + Rec.709 原色 + D65 + 16F

- 一期内容基本落在 P3 以内，用 709 原色中转不会有可见损失（float 下矩阵可逆，负值只在最终输出才裁剪）；
- 16F 有足够余量表达 >1.0 的高光，二期 HDR 不需要换管线，只在 Pass 2 前插一步色调映射；
- 与 `scRGB` 的语义一致，将来切 HDR 交换链时数学不用改。

替代方案（线性 BT.2020 工作空间）见 [ADR-0004](adr/0004-self-implemented-color-management.md)。

### 4.2 显示侧：一期假定 sRGB

一期不做 ICC 读取，假定目标显示为 sRGB / 2.2 附近。理由：先把链路跑通、把双后端一致性做出来，比先做 profile 管理收益高。

二期再引入：`GetICMProfile` / `WcsGetDefaultColorProfile` 取显示 profile → 解析 `wtpt`/`rXYZ` 等 tag → 生成 Pass 2 的目标矩阵与 TRC。**这一步属于二期，不提前写。**

### 4.3 DXGI 的色彩空间只是"声明"

`IDXGISwapChain3::SetColorSpace1` 不改变像素，它告诉 DWM 该如何解释这些像素。所以：

- 我们**必须**把交换链声明的色彩空间与 Pass 2 的实际输出对齐，否则系统会二次解释；
- 但**不能**指望它做转换。转换全在 Pass 2。

这个区分是整条链路最容易出错的地方，[ADR-0007](adr/0007-swapchain-format-and-color-space.md) 专门记录。

### 4.4 Skia 侧如何确保"零自动转换"

Skia 的颜色管理只发生在 **image → surface** 的转换上。要让它不插手，需同时满足：

1. 传入 Skia 的纹理/图像不带会让它做转换的色彩空间（或显式声明为与输出相同）；
2. `SkSurface` 声明的色彩空间 == Pass 2 的输出空间；
3. 所有转换在 `SkRuntimeEffect` 内完成。

**这是待验证假设**（M3 出口条件之一）：用像素探针（纯色 1×1 图，已知输入）在读回后比对，确认 Skia 未插入转换。未验证前不得在文档里写成"已确认"。

## 5. 已知陷阱（踩过就补一条）

| # | 陷阱 | 症状 | 处置 |
|---|---|---|---|
| 1 | 把 sRGB 当 gamma 2.2 | 暗部偏亮 ~2% | 用精确分段函数，见 SPEC §3.1 |
| 2 | 忘做 limited→full 归一化 | 黑位发灰、白位不够白 | 归一化必须是 Pass 1 第一步 |
| 3 | YUV 矩阵猜错（内容标 709 却用 601） | 肤色偏绿/偏紫 | 一律从 `ColorMetadata.matrix` 取，不设默认值 |
| 4 | 在非线性空间做缩放/混合 | 边缘发暗、色带 | 缩放只在 Pass 2 采样时做，或在线上空间做 |
| 5 | 交换链声明与输出不一致 | 整体发灰或过饱和（DWM 二次处理） | 见 ADR-0007，加启动自检日志 |
| 6 | 8-bit 直接输出线性值 | 严重色带 | 编码 + 抖动，见 SPEC §6 |
| 7 | 白点适应漏做（ICC 为 D50） | 整体偏黄 | 有 ICC 时必须 Bradford |

## 6. 范围边界

**一期（SDR）**：sRGB、gamma 2.2、Display P3 的输入与输出；YUV 601/709；8/10-bit；抖动。

**二期（HDR）**：PQ、HLG、BT.2020、HDR10 静态元数据、系统 HDR 开关检测、SDR 内容的 HDR 呈现策略。

**明确不做**：色彩外观模型（CAM16）、感知均匀空间下的编辑、打印机色彩、3D LUT 文件格式。

## 7. 验收标准

1. 双后端对同一帧的最大像素差 ≤ 1 LSB（目标位深）。
2. 与 CPU 双精度参考实现相比，SDR 路径 ΔE00 ≤ 0.5。
3. 灰阶渐变图在 8-bit 输出下无可见色带（8×8 Bayer 抖动后）。
4. 上述三条必须能在 CI 之外的本地机器上一键复现（见 [TESTING.md](TESTING.md)）。
