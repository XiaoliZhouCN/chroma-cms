# 0003. 双渲染后端共享同一个 D3D12 设备

- **状态**：accepted
- **日期**：2026-11-04
- **决策者**：XiaoliZhouCN

## 背景

学习目标要求**对比两条渲染路径**：

1. 原生 D3D12：自己管交换链、PSO、根签名、命令列表、fence；
2. Skia D3D12：Skia 的 Ganesh 后端产出绘制命令，我们在其之上跑 SkSL runtime effect。

要"对比"，必须排除无关变量：设备差异、交换链格式差异、驱动状态差异，都会让像素差异无法归因到"实现差异"。

## 决策

1. 抽象 `IRenderer`，两个实现：`D3D12Renderer`、`SkiaD3D12Renderer`；
2. **两个后端共用同一个 `ID3D12Device`、同一个命令队列、同一张交换链**；
3. Skia 侧通过 `GrD3DBackendContext` 注入已有设备/队列/适配器 LUID，不让 Skia 自己建设备；
4. 后端可在运行时切换，切换不重建窗口、不重建设备；
5. 双后端一致性测试因此可以在一次进程内完成。

## 后果

### 正面

- 差异只可能来自"命令录制方式"与"着色器实现"，归因清晰；
- 一致性测试成本低（同帧、同设备、同格式）；
- 学到 Skia 如何被"嵌进"已有 GPU 架构，而不是只能整包使用。

### 负面 / 代价

- 两个后端都受同一条命令队列约束，无法测量各自的吞吐上限；
- Skia 的设备初始化假设可能与我们的用法冲突（如队列类型、fence 语义），需要验证；
- `IRenderer` 抽象若做得过薄会泄漏 D3D12 类型，过厚则掩盖学习细节——约束是"接口不出现 D3D12 类型"。

### 需要跟进

- [ ] **【待验证】** `GrD3DBackendContext` 在当前 Skia 版本接受外部设备/队列的确切签名。
- [ ] **【待验证】** Skia 是否允许直接 wrap 交换链后台缓冲为 `SkSurface`（[../ROADMAP.md](../ROADMAP.md) Q2）。
- [ ] 若上述任一不成立，需新建 ADR 调整呈现路径（例如 Skia 渲染到离屏纹理再拷贝）。

## 替代方案

| 方案 | 否决理由 |
|---|---|
| 两个后端各建设备 | 设备/驱动状态差异污染对比结论，一致性测试失去意义 |
| 只做原生 D3D12 | 失去"同一数学两种实现"的核心学习目标 |
| 只做 Skia | 学不到交换链、fence、呈现节奏这些底层细节 |
| 双进程分别运行 | 无法保证同一帧、同一设备状态，比对成本高 |
