# 协作协议（人 × Agent）

> 这份协议解决一个问题：**让每次会话的产出可累积，而不是每次都从环境重新猜。**
> 硬规则在 [AGENTS.md](../AGENTS.md)，这里写流程。

## 1. 角色

| 角色 | 谁 | 职责 | 不做 |
|---|---|---|---|
| **Owner** | 人类 | 定方向、批"需人工确认"的变更、评审关键 diff | 不手写重复性文档 |
| **Implementer** | Agent | 实现、验证、同步文档、写 ADR | 不擅自扩大范围 |
| **Reviewer** | 人类或另一个 Agent | 按 §6 清单审提交 | 不做"看起来没问题"式放行 |

## 2. 任务协议（每次工作都走这五步）

```
1. 领任务    — 明确：要改什么、为什么、验收标准是什么
2. 声明范围  — 分支名 + 允许写的路径 + 预计碰到的文档
3. 实现      — 先文档（ADR）后代码；小步提交
4. 自验      — 构建 / ctest / check-docs / 一致性测试
5. 交付      — 提交 + 会话记录 + （有决策则 ADR）
```

**第 2 步不可跳过。** 没有范围声明的任务，冲突和返工是必然的。

### 范围声明的格式

```
任务：实现 Pass 1 的 sRGB 解码
分支：feat/pass1-srgb-decode
写范围：src/color/*、shaders/hlsl/*、tests/color/*
预期文档：COLOR_SPEC.md（不改，仅对照）、SESSION_INDEX.md（收工追加）
验收：SPEC §8 A1–A4 通过；ctest -R color 绿
```

## 3. 四个仪式

### 3.1 开工

1. 读 [AGENTS.md](../AGENTS.md) 的硬规则与授权矩阵。
2. 按"按场景读文档"表，只读**本次相关的**文档（不通读）。
3. 看 [SESSION_INDEX.md](SESSION_INDEX.md) 最后一条的"下次第一件事"。
4. 写范围声明（见 §2）。

### 3.2 变更

- 产生技术取舍 → 先写 ADR，`status: proposed`，再写代码。
- 代码与受影响文档**同一个提交**。
- 一次提交只做一件事；重构与功能分开。

### 3.3 收工

1. 跑完 [AGENTS.md](../AGENTS.md) §4 的 DoD。
2. 在 [SESSION_INDEX.md](SESSION_INDEX.md) **追加**一条（模板见 [templates/SESSION_ENTRY.md](templates/SESSION_ENTRY.md)）。
3. 未完成的事必须落到：ROADMAP 的待决表、ADR 的 proposed、或"下次第一件事"字段——**不许只留在对话里**。

### 3.4 评审

按 §6 清单逐条过，任一不满足即打回。

## 4. 多 Agent 并发规则

| 规则 | 说明 |
|---|---|
| **单写者** | 同一文件同时只允许一个 Agent 写。共享文档（SESSION_INDEX、INDEX、ROADMAP）原则上一人写。 |
| **共享台账只追加** | SESSION_INDEX、ADR 编号：只 append，不改历史，避免丢失更新。 |
| **契约先冻结** | 两个 Agent 要并行实现同一接口的两侧时，先把接口写进文档/ADR 并冻结，再各自实现。 |
| **范围不相交** | 并行任务的文件路径不得重叠；重叠就串行。 |
| **合并靠 rebase** | 禁止 merge commit；冲突由最后 rebase 的人解决并重跑测试。 |
| **Lead 统一收口** | 多 Agent 场景由 Lead 汇总 diff、跑最终验证，其他人不直接改 `develop`。 |

## 5. 升级规则

遇到以下情况**停下来问 Owner**，不要自行决定、不要猜：

1. 命中 [AGENTS.md](../AGENTS.md) §2 的"需人工确认"档位；
2. 要修改 [COLOR_SPEC.md](COLOR_SPEC.md) 的公式或常量；
3. 文档与代码矛盾且无法从 ADR 判定谁对；
4. 发现需要一个新依赖；
5. 出口条件无法验证（比如没有可用的 GPU）。

停下来是正确行为。**猜出来的结果比没有结果更贵**——它会污染后续所有会话的判断。

## 6. 评审清单

- [ ] 改动是否落在声明的范围内？超范围的改动是否单独立项？
- [ ] 颜色数学是否只存在于 `shaders/` 与 `src/color/`？有无框架自带色彩管理混入？
- [ ] HLSL 与 SKSL 是否同步（若触及颜色）？
- [ ] 是否有对应的测试？修 bug 是否补了回归用例？
- [ ] 受影响的文档是否同步？是否有该写而未写的 ADR？
- [ ] `check-docs` 是否通过？
- [ ] 提交信息是否符合 Conventional Commits？
- [ ] SESSION_INDEX 是否追加？

## 7. 反模式（出现即返工）

| 反模式 | 为什么有害 |
|---|---|
| 只改代码不改文档 | 下次会话会按旧文档办事，错误被固化 |
| 把结论只写在对话里 | 会话结束即丢失，等于没发生 |
| 一次性重写大段文档 | 无法评审，且会覆盖别人的增量 |
| 为了让测试变绿而放宽容差 | 容差是验收标准，不是障碍 |
| 在 `present()` 里临时 `new` | 渲染路径抖动、帧时间不可预测 |
| 用 Skia / Qt 的转换"先跑通" | 违反 ADR-0004，且后期拆不干净 |
| 空文件/占位文档 | 会让 Agent 误以为"已读过规则" |

## 8. 会话记录字段

见 [templates/SESSION_ENTRY.md](templates/SESSION_ENTRY.md)。核心是四个字段：

`目标` / `产出` / `未决` / **`下次第一件事`**

最后一项是这份台账存在的理由——它让下一次会话的启动成本从"重新探索"降到"读一行"。
